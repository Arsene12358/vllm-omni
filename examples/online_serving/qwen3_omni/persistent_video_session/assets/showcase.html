What it does

The model watches a video as it streams. At any time you can ask a question; it answers about what is happening right now and can still reference what it saw at the beginning, no matter how long the stream has been running. Crucially, GPU memory does not grow with stream length — so the same box can keep a session online indefinitely (bounded, "reasonably-large" sessions).

How it works

One persistent engine request (an "epoch") ingests frames as small input-only chunks. A streaming-LLM KV eviction policy keeps only a pinned opening ("sink") plus a sliding recent window — everything between is dropped, so the cache stays bounded. Queries generate against that retained cache. When the rotary-position budget for an epoch is reached, the session refreshes: a fresh request is re-seeded with the opening + recent frames, position resets, and ingestion continues — the opening is preserved across the boundary.

🔒 The opening is pinned and re-seeded every refresh — that is why "what was at the very beginning?" keeps working after hours of stream and many refreshes.

Bounded memory — the always-online property

Without eviction, the KV cache grows with every frame and the session eventually exhausts GPU memory. With the streaming-LLM eviction here, the live cache stays flat: it only ever holds the pinned opening plus the recent window. Measured live across all 10 epochs of the run, the live block count never left 672–673 (pinned opening = 160 blocks) while the total tokens processed climbed into the tens of thousands per epoch.

How to read this / how to verify it yourself

  • Current-moment tracking — the (a) answers should change as the video progresses (they do: archway → alien landscape → boss fight → victory).
  • Opening retention — the (b) answers should stay about the opening, the same across refreshes (they do).
  • Bounded memory — the server log's [streaming-kv] eviction … alive=N line should stay flat as the stream grows; new vsess-…-<epoch> ids mark refreshes.
  • No crash — the session ends cleanly (session.done) with zero errors.

Honest caveats

  • Throughput is realtime-capable. Measured on this 2×H200 setup (eager execution, no CUDA graphs yet): ingestion runs at ~25 frames/s — about 12× a live 2 fps feed, and a query returns in ~1.5 s (after a one-time warmup). So a single session comfortably keeps up with a live feed. Higher frame-rates / resolution and many concurrent sessions are headroom to characterize, and further speedups (CUDA graphs, coarser ingest chunks, batching) remain available — but are not required to be realtime here.
  • Answer style is the base model's. Qwen3-Omni is verbose (it sometimes appends a "Detailed Breakdown") and its content/labels (e.g. naming the game) are the base model's behavior, independent of the streaming layer. A brevity instruction in the system prompt tightens this.
  • Bounded, not literally infinite. The session is reasonably-large and refreshes indefinitely; resources stay bounded throughout.
